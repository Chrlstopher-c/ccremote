Mise en production ccremote — 19 août 2026

Ce que la nuit a changé, et ce qu'il vous reste à faire

Trois chantiers cette nuit — deux sur ccremote, un sur Vigie — tous fusionnés localement et testés. Mais le PC du parc (trinityarch) était éteint cette nuit, et le déploiement vers le Pi part toujours de ce PC. Avant de lire le reste de ce document, faites d'abord l'étape 0 ci-dessous : allumer le PC et le mettre à jour. Sans ça, la mise en production du Pi enverrait une version du dépôt qui n'a pas le travail de cette nuit.

Étape 0 — avant tout, remettre le PC à jour

Cette étape se fait à la main, sur place : le paquet de réveil réseau envoyé cette nuit n'a pas suffi à rallumer le PC. Elle ne prend que quelques minutes, et elle conditionne tout le reste — ne passez à la mise en production du Pi qu'une fois les quatre points ci-dessous validés.

1

Allumer le PC

Sur place — la tour du PC (trinityarch)

Appuyez sur le bouton d'alimentation de la tour, comme pour n'importe quel démarrage. Attendez l'affichage complet du bureau (une petite minute) avant de passer à la suite.

2

Ouvrir un terminal et récupérer le travail de cette nuit

Sur le PC — /mnt/projects/ccremote

cd /mnt/projects/ccremote
git pull --ff-only origin master
bun install

La première commande vous place dans le dossier du projet. La deuxième va chercher le travail de la nuit sans jamais rien écraser sur le PC — si elle affiche un message d'erreur au lieu d'une liste de fichiers modifiés, arrêtez-vous là, quelque chose d'anormal s'est produit. La troisième installe ce dont ce travail a besoin pour fonctionner.

3

Redémarrer le superviseur du PC sur ce nouveau code

Sur le PC — /mnt/projects/ccremote

./deploy-superviseur-pc.sh

Ce script redémarre le service qui fait tourner le PC — une coupure de quelques secondes, sans conséquence : aucune équipe n'y travaille à cette heure-là.

Deux lignes doivent apparaître dans ce qu'affiche la commande : une qui commence par ✓ process démarré le, une qui commence par ✓ Superviseur du PC actif. Si l'une des deux manque, ou si un message d'erreur apparaît à la place, le PC n'est pas à jour — ne passez pas à la suite.

4

Vérifier que le PC est bien reconnecté

Sur le PC — /mnt/projects/ccremote

bun harness/pilotage/pilote.ts machines

Cherchez la ligne qui contient pc : elle doit commencer par un point plein ●, pas un point vide ○. Le point plein confirme que le PC est bien en ligne avec le code du jour. S'il est vide, attendez une minute et relancez la commande avant de continuer.

Une fois ces quatre points validés, le PC porte le travail de cette nuit — vous pouvez enchaîner directement sur la mise en production du Pi plus bas, exactement comme décrit.

Ce qui a été fait

01

Une décision qui vous attend ne se cache plus

Quand l'orchestrateur propose un mandat qui exige votre feu vert, ce fait est désormais écrit tout de suite.

  • Avant Une proposition en attente de votre autorisation n'existait nulle part avant que vous n'ouvriez l'app — vous ne pouviez découvrir qu'une décision vous attendait qu'en tombant dessus par hasard dans le fil.
  • Maintenant Le fait est journalisé au moment même où la proposition est écrite, sans attendre que vous ouvriez quoi que ce soit — c'est ce qui permettra de vous le signaler activement.
02

Une session expirée se le dit clairement, sur iPhone

Le client iOS (Vigie) sait maintenant reconnaître une déconnexion pour ce qu'elle est.

  • Avant Quand votre session avait expiré, le serveur répondait à Vigie par la page web de connexion — que l'app tentait de lire comme si c'était sa réponse normale, sans rien comprendre à ce qu'elle recevait.
  • Maintenant Le serveur répond clairement « session expirée » à Vigie, qui peut vous le dire proprement et vous proposer de vous reconnecter. Le reste de l'interface web (le navigateur) continue de fonctionner exactement comme avant.
03

Les notifications rattrapent une absence, sans trou

Revenir après un moment d'absence ne vous fait plus perdre les plus anciennes.

  • Avant Seules les notifications les plus récentes étaient renvoyées à l'ouverture. Après une absence un peu longue, tout ce qui dépassait ce plafond disparaissait silencieusement — jamais vu, jamais rattrapé.
  • Maintenant Vigie peut demander « tout ce qui est arrivé depuis ma dernière notification vue » : le serveur renvoie la suite complète, dans l'ordre, sans plafond qui en perdrait en route.
04

L'orchestrateur peut vous montrer un script ou une page, dans le fil

Un contenu que l'orchestrateur produit lui-même s'affiche désormais comme une pièce du fil, pas comme un pavé de texte.

  • Avant Un script ou une page HTML produits par l'orchestrateur n'avaient pas de forme dédiée : soit du texte brut noyé dans la réponse, soit rien de consultable directement dans la conversation.
  • Maintenant Sur le web comme dans Vigie, ce contenu apparaît comme une carte du fil — nom, langage, code en clair, et pour une page HTML un aperçu rendu à côté du code. Dans Vigie, ce rendu est isolé (mémoire non persistante, aucune navigation possible en dehors, votre session ne lui est jamais exposée) puisque le contenu vient de l'orchestrateur et n'est pas fiable par défaut.
Les quatre chantiers sont fusionnés sur les branches principales locales de ccremote et de vigie, avec leurs suites de tests au vert (1 797 tests côté harness, 135 côté Vigie) et l'IPA de Vigie recompilée sans erreur. Pour voir la carte d'artefact dans Vigie sur votre iPhone, il faudra réinstaller l'app via votre flux habituel (build.sh / Impactor) — ce n'est pas lié à la mise en production du Pi ci-dessous.

Mise en production sur le Pi

Tout se lance depuis le PC, dans /mnt/projects/ccremote — c'est de là que les scripts de déploiement envoient les fichiers vers le Pi. Une seule commande fait tout le travail ; le détail ci-dessous vous dit ce qu'elle redémarre et comment vérifier après coup.

1

Vérifier que le PC a bien le code de cette nuit

Sur le PC — /mnt/projects/ccremote

cd /mnt/projects/ccremote
git status
git log -1 --oneline

git status doit répondre « rien à valider, la copie de travail est propre » — deployer-pi.sh refuse de partir sur un arbre sale. Si une équipe suivante a fait son travail cette nuit, le dernier commit doit être visible ici.

2

Prévisualiser (facultatif, mais gratuit)

Sur le PC — /mnt/projects/ccremote

./deployer-pi.sh --simulation

N'exécute rien : affiche si le secret du lien est résoluble et si l'interface web (pi-web/) sera redéployée ou non.

3

Déployer, pour de vrai

Sur le PC — /mnt/projects/ccremote

./deployer-pi.sh

Enchaîne deux choses automatiquement : le control plane du Pi (toujours), puis l'interface web (pi-web) seulement si elle a changé depuis son dernier déploiement — c'est le cas cette nuit (notifications, session iOS, artefacts y touchent tous).

Ce qui redémarre et se coupe brièvement (quelques secondes chacun) : le service ccremote-harness sur le Pi (registre, API web du harness, lien avec le PC/le VPS — ces derniers se reconnectent seuls après coup), puis le service ccremote-web (l'interface publique ccremote.exemple.com, y compris ce que Vigie consomme). Les autres tunnels du Pi (StockIOP, CRM, license-server) ne sont pas touchés sauf si une règle d'exposition change — pas le cas ici.

Le secret du lien PC↔Pi est résolu tout seul depuis ~/.config/ccremote/pc.env — rien à saisir à la main.

4

Vérifier que ça a réellement pris

Sur le PC — la commande elle-même vérifie déjà une partie

✓ process démarré le <heure>, postérieur à toutes les sources
✓ Pi déployé : control plane actif, redémarré, postérieur à ses sources.

Ces deux lignes doivent apparaître dans la sortie du script — pas seulement « ça s'est terminé sans erreur ». Si l'une manque, le déploiement a échoué quelque part au-dessus dans le journal du terminal.

Pour l'interface web (pas de vérification automatique intégrée)

curl -sI https://ccremote.exemple.com/ | head -1

Doit répondre HTTP/2 200 (ou une redirection 303 vers /login si vous n'êtes pas connecté depuis ce poste — les deux prouvent que le service répond). Un curl: (7) Failed to connect ou un 502 veut dire que ccremote-web n'est pas remonté.

5

Si ça ne prend pas

Sur le PC, selon le message affiché par le script

# arbre de travail sale
git status                      # commit ou stash, puis relancer

# secret introuvable
cat ~/.config/ccremote/pc.env | grep CCREMOTE_LIEN_SECRET
# doit être NON VIDE et identique à celui déjà sur le Pi — jamais en régénérer un

# process périmé / échec du health check
ssh -i ~/.ssh/id_ed25519_ccremote pi@pi.exemple \
  "sudo journalctl -u ccremote-harness -n 80 --no-pager"

Pour l'interface web, même idée avec le service ccremote-web : sudo journalctl -u ccremote-web -n 80 --no-pager sur le Pi. Dans les deux cas, relancer ./deployer-pi.sh une fois la cause corrigée est sans risque — le script est idempotent et refuse de partir sur un état qu'il ne comprend pas plutôt que de deviner.

Ce que cette commande ne touche pas — le portable et le VPS (leurs superviseurs de workers) ne sont pas concernés par deployer-pi.sh, qui ne parle qu'au Pi. En dehors de l'étape 0 en tête de ce document (qui remet le PC à jour), rien ici ne suppose que vous avez à toucher au portable ou au VPS demain.
